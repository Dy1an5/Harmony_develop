# 04 从安卓迁移

把现有 Android 应用变成原生鸿蒙应用。**先看结论，再看路线。**

## 一、技术前提（先接受这三个事实）

1. **HarmonyOS NEXT 起不再基于 Android，不兼容 APK，无法直接安装运行。**
   华为**没有**提供 Android → 鸿蒙 的一键迁移工具。UI 和业务逻辑要重写，Java/Kotlin 代码直接复用不了。
2. HarmonyOS 6 及以上可以通过第三方虚拟化容器（如卓易通）跑 Android 应用，但那是"兼容运行"，
   **不是鸿蒙原生应用，通常也无法作为原生鸿蒙应用上架**，只能算过渡手段。
3. 能复用的路径只有一条：**通过平台桥接把原生能力调回去**（见下文第四节）。

## 二、四条路线怎么选

| 路线 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. ArkTS 原生重写**（推荐） | 用 ArkTS + ArkUI 重写整个应用 | 能力最完整、性能最好、审核最顺 | 工作量最大，UI 和业务都要重写 |
| **B. ArkUI-X 跨平台** | 一套 ArkTS 代码同时产出 HarmonyOS / Android / iOS；通过「平台桥接」复用现有 Android 原生代码 | 一份代码多端；能渐进式复用旧原生能力 | 需改造工程结构；只有跨平台 API 子集可用；桥接有数据类型和性能约束 |
| **C. 虚拟化容器** | 卓易通等兼容层跑现有 APK | 零改造 | 不是原生应用，体验和上架都受限 |
| **D. 社区跨端框架** | uni-app / Taro / Flutter 的鸿蒙适配 | 复用已有跨端代码 | 非华为官方方案，长期维护性和能力覆盖需自行评估 |

**如果目标就是"发行原生鸿蒙应用"，实际可选的是 A 或 B。**

B 的核心价值是让你**不必一次重写所有东西**：UI 用 ArkTS 重写，短时间搞不定的原生能力
（已有 Java 三方库、平台私有能力）先通过平台桥接调回去，后续再逐步替换。

> **本仓库的结论是走 A（ArkTS 原生重写）。** 理由：调试目标是鸿蒙平板，
> 现有安卓包只能靠兼容层跑，上架必须是原生应用（2026-10-15 定）。

## 四、平台桥接（路线 B 的关键）

ArkUI-X 提供的 `@arkui-x.bridge` 用于 ArkUI 与 Android / iOS 之间**双向通信**。原理上 ArkTS 与 Java
由 C++ 中转，但对开发者就像直接互调。

### 能干什么

1. ArkUI 与平台**双向传数据**（JSON、图片等）；
2. ArkUI 侧**调用平台 API**（如复用已有 Java 三方库）；
3. 平台**调用 ArkUI 侧方法**。

**只覆盖非 UI 的跨平台 API 子集，UI 相关不覆盖。**

### 数据类型与上限

编解码两种模式：**JSON（默认）** 和**二进制**（多支持一个 `ArrayBuffer`）。
支持 `string` / 整数 / 浮点 / `boolean` / 数组 / `Record<string, S>`（S 仅 string / number / boolean）。硬上限：

| 限制 | 值 |
| --- | --- |
| `string` 单次传输 | **2 MB** |
| `ArrayBuffer` 单次传输 | **20 MB** |
| 数字范围 | **−2^53+1 ~ 2^53−1**，跨端注意精度 |
| `ArrayBuffer` | **只能单独使用**，不能包在 Array / Record 里 |

### 调用时机（**SDK ≥ 6.0.2.118 的口径**）

- **创建 Bridge**：ArkUI 侧在 `UIAbility.onCreate()` 内或之后；Android 侧在 `StageApplication.onCreate()` 之后
  或 `AppDelegate.initApplication()` 之后。
- **调用接口**：ArkUI 侧在 `UIAbility.onCreate()` **执行完毕后**；Android 侧在 `Activity.onCreate()` **执行完毕后**。

> ⚠️ **SDK < 6.0.2.118 时口径不同**：Bridge 绑 Activity 生命周期，ArkUI 侧接口调用要在 `onWindowStageCreate()` 之后。
> 升级 SDK 前先看原文对应小节。
>
> ⚠️ **别把出处搞混**：上面这四条出自**《平台桥接开发指南（Android）》的「SDK 版本大于 6.0.2.118」一节**，
> 原文已收录为 [references/arkui-x/平台桥接开发指南-Android.md](../references/arkui-x/平台桥接开发指南-Android.md)。
> **《平台桥接介绍》那篇只讲使用场景和数据类型表，不含创建时机。**

### 四个场景的代码骨架

```typescript
// ArkUI 侧：创建 Bridge 实例（JSON 模式；二进制传第二个参数 BridgeType.BINARY_TYPE）
import bridge from '@arkui-x.bridge';

const bridgeImpl: bridge.BridgeObject = bridge.createBridge('BridgeName');

// 场景一：ArkUI → Android 传数据
bridgeImpl.sendMessage('data').then((res) => { /* Android 侧回执 */ });

// 场景二：接收 Android 传来的数据
bridgeImpl.setMessageListener((data: bridge.Message) => {
  console.log('data: ' + JSON.stringify(data));
  return 'ArkTS Received';           // 返回值就是回执
});

// 场景三：调用 Android 侧方法
bridgeImpl.callMethod('platformCallMethod').then((res) => { /* 返回值 */ });

// 场景四：注册方法供 Android 侧调用
private getArkTSData(param: number): bridge.ResultValue { return 'ok'; }
bridgeImpl.registerMethod({ name: 'getArkTSData', method: this.getArkTSData });
```

```java
// Android 侧：构造 Bridge 实例
BridgeImpl bridgeImpl = new BridgeImpl("BridgeName", BridgePlugin.BridgeType.JSON_TYPE);
bridgeImpl.setMessageListener(new BridgeMessageListener());   // 场景一/二的接收侧
bridgeImpl.callMethod("getArkTSData", 100);                    // 场景四：调 ArkUI 侧方法
```

## 五、实施步骤

**S0 评估**（最该花时间的一步）

- 清点模块：哪些是纯 UI、哪些是业务逻辑、哪些是平台原生能力。
- **盘点第三方 SDK 有没有鸿蒙版本**，没有的提前规划平台桥接或替代方案 —— 越晚发现越贵。
- 确认哪些能力个人开发者拿不到（一键登录、手机号、收货地址等，见[备案与资质要求](../备案与资质要求.md)）。

**S1 工程骨架**

- 建 Stage 模型工程（Linux 命令行建法见 [工具链 / 01](../toolchain/01-环境搭建.md)）。
- **确定 `bundleName`**，与备案、软著名称规划一致，定了别改。
- 配好调试签名。

**S2 UI 重写**

- 页面拆成 ArkUI 组件，先搭静态布局，再接数据。
- 平板优先用 `Navigation` 分栏。
- 状态管理按 [03](03-ArkTS与ArkUI基础.md) 的规则来。

**S3 业务逻辑**

- 数据层：网络、缓存、数据库。
- 复用旧逻辑时优先考虑平台桥接。

**S4 系统能力接入**

- 权限、通知、定位、推送、支付、账号。

**S5 测试**

- DevEco Testing + 云测试 / 云调试，覆盖多设备形态。

**S6 上架准备**

- 换发布证书打包，走[开发者注册与上架发行](../01-开发者注册与上架发行.md)。

## 六、常见坑

1. **思维模式**：ArkUI 是声明式 + 状态驱动，不要照搬"拿到 View 再 setText"。
2. **ArkTS 不是完整 TypeScript**：`any`、运行时改对象、结构类型放宽都会被编译期拦下。见 [03](03-ArkTS与ArkUI基础.md)。
3. **构建体系换了**：Gradle → hvigor，依赖配置在 `oh-package.json5`。
4. **第三方库缺口**：先做依赖盘点，越早发现越好。
5. **调试证书绑设备**：换机器 / 加设备要重新登记，团队协作提前规划。
6. **平台桥接不是万能**：只覆盖跨端 API 子集，UI 不覆盖，大数据量有上限。
7. **包名一次性规划好**：`bundleName` 与备案、软著、商店名称的对应关系一旦定下，改动成本很高。
8. **`compatibleSdkVersion` 要 ≤ 目标设备系统版本**，否则装不上。
