# 06 打包与签名工作流

**两条路，别混**：

| 用途 | 证书 | 怎么来 | 能不能装真机 |
| --- | --- | --- | --- |
| **日常调试** | 调试证书 | `devecocli signature generate` 自动签名 | 能（设备 UDID 要在白名单里） |
| **上架** | **发布证书** | **必须手动申请**（keytool → AGC） | **不能** |

自动签名永远拿不到发布证书，而手动那条路有几个自动签名遇不到的坑。本文记录完整走法。

> 全部结论来自在 MDwell 上把发布包打出来的完整实操（2026-10-19，本机）。

---

# 第一部分：调试签名（一次性，日常用）

```bash
devecocli auth login
devecocli signature generate --product default
```

它会生成 p12/csr、去云端换证书、下载 p7b，并把这些写进 `build-profile.json5`。

## 签名坑 0：CLI 的 `signature generate` 有个鸡生蛋的设备预检

**这条是 CLI 独有的，不能拿 DevEco Studio 的经验套。**

它签之前会查「AGC 云上本团队是否已有设备」；没有就回退查本地 `hdc`，
**但本地 USB 真机不算数**（只认模拟器 serial `127.0.0.1:*`）→ 直接抛 `DEVICE_MISSING` 硬停。
而它内部本来有个「把本地设备自动加进 AGC」的步骤，却跑在预检**之后**，被提前掐断。

表现很有迷惑性：`devecocli device list` / `device view` 都能正常看到平板，**所以这不是设备识别问题**。

> **解法**：先去 AGC 网页把平板 UDID 加为调试设备（一次即可，之后云上非空就放行了）。
> 拿 UDID：`hdc shell bm get -u`。

## 签名坑 1：联网子命令会被代理静默搞坏

凡联网子命令（`auth` / `signature` / `update` / `emulator image` / `create`）都套一层：

```bash
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY devecocli auth status
```

详见 [05](05-调试工作流与命令.md) 与 [07](07-踩过的坑.md) 坑 2。

## 签名坑 2：`build-profile.json5` 不能整个提交，也不能整个忽略

它同时含**构建必需**的 `products` / `modules` 配置（必须进 Git）和**签名后写进去的加密密码**（不能进 Git）：

```bash
git update-index --skip-worktree build-profile.json5
```

**把它写进 `.gitignore` 是个常见错误。** 同理，签名材料（`*.p12` / `*.cer` / `*.p7b` / `*.csr`）**一律不提交**。
详见 [07](07-踩过的坑.md) 坑 5。

## 签名坑 3：自动签名拿不到按「应用身份」授权的服务

表现是构建、安装、启动都正常，**地图瓦片一片空白且不报错**（如 Map Kit 花瓣地图）。

正确做法：保留自动签名生成的密钥对，去 AGC 为真实应用建一个 debug Profile
（包名、APP ID、证书、调试设备 UDID 都要对），下载 p7b 后把 `build-profile.json5` 的 `profile:` 指过去。

验证：`hdc shell bm dump -n <包名>`，看 `appIdentifier` 是否与 AGC 一致。

## 签名坑 4：签名身份决定应用数据

换签名安装会被视为全新安装，`/data/app/el2/100/base/<包名>` 的 uid 变了，应用设置全丢。

- 跨机器（Windows 上 DevEco 签一套、Linux 上 CLI 签另一套）交替安装 = 数据反复被清。
- 想让多平台共用，就把 p12 + p7b 同步过去。

> **推论**：调试签名与发布签名要**两套并存**（加独立的 `signingConfigs` + `product`），
> 而不是把调试那套换掉 —— 见下面「坑 E」。详见 [07](07-踩过的坑.md) 坑 4。

## 另外两个容易踩的

- **系统时间要对到秒。** 签名失败报
  `The signature does not take effect or has expired. The current system time may be inaccurate. Please calibrate the system time and sign again.`
  时，原因是**本机时间与服务器时间不一致**，不是证书坏了。官方要求与北京时间比对，精确到 1–2 秒。
- **别用 `devecocli run --uninstall`** —— 会把应用 `preferences/` 整个删掉，等于换签名安装的效果，数据全丢。

# 第二部分：手动申请发布证书

## 步骤

**1. 生成密钥和证书请求文件（CSR）**

```bash
keytool -genkeypair -alias <别名> -keyalg EC -sigalg SHA256withECDSA \
  -dname "C=CN,O=<组织>,OU=<部门>,CN=<名称>" \
  -keystore <名>.p12 -storetype pkcs12 -validity 9125 \
  -storepass <密码> -keypass <密码>

keytool -certreq -alias <别名> -keystore <名>.p12 -storetype pkcs12 \
  -storepass <密码> -file <名>.csr
```

- **`-keyalg` 必须是 `EC`**。用 RSA 生成的 CSR 传到 AGC 会被判「上传的 CSR 文件无效」
  （官方 FAQ `faqs-appgallery-69` 点的就是这个）。
- 密码规则：大写 / 小写 / 数字 / 特殊符号中**两类以上**组合，**≥ 8 位**。
- `-validity 9125`（25 年）是覆盖应用生命周期的写法 —— **但 AGC 签发时固定给 3 年**，与 p12 里写多少无关。

**2. 在 AGC 申请发布证书**

先在 AGC 建好应用（`bundleName` 要对）→「证书、App ID 和 Profile」→ **证书** → 新增 → 上传 `.csr` → 下载 `.cer`。

**3. 在 AGC 申请发布 Profile**

同一页 → **Profile** → 新增 → 类型选 **Release** → 选应用和刚申请的证书 → 下载 `.p7b`。

> Release 类型的 Profile **不需要选设备** —— 设备白名单只有调试 Profile 才有。

**4. 配进工程**：见下面「坑 E」。

## 坑 A：JDK 21 下 `-keyalg EC` 默认生成 **P-384**，不是 P-256

```
$ keytool -genkeypair -alias t -keyalg EC -sigalg SHA256withECDSA ...
Generating 384 bit EC (secp384r1) key pair and self-signed certificate (SHA256withECDSA)
```

- 华为命令行文档给的示例带 `-groupname secp256r1`（P-256）；**JDK 21 不带这个参数时默认是 secp384r1**（P-384）。
- **两者 AGC 都接受** —— 华为自己的 `devecocli signature generate` 生成的调试证书也是 P-384
  （`openssl x509` 看 `ASN1 OID: secp384r1`）。
- **所以看到 P-384 不是配错了**，不用回头重做。想要 P-256 就显式加 `-groupname secp256r1`。

## 坑 B：下载的 `.cer` 是**三张证书的链**，不是一张

```
$ openssl x509 -in xxx.cer -noout -subject
subject=C=CN, O=Huawei, OU=Huawei CBG, CN=Huawei CBG Root CA G2      ← 读到的是根 CA
```

`openssl x509` 默认只读**第一张**，而链的顺序是「根 CA → **叶证书（你的）** → 中间 CA」。
**叶证书在链中第 2 张** —— 别据此以为下错文件了。要列出整条链：

```bash
openssl crl2pkcs7 -nocrl -certfile xxx.cer | openssl pkcs7 -print_certs -noout
```

## 坑 C：AGC 会用**账号实名信息覆盖** CSR 里的 subject

CSR 的 dname 填 `O=MDwell, CN=MDwell`，签出来的证书是 `O=<账号实名>, CN=<账号实名>(<开发者ID>)\Release`。

**dname 填什么都不影响结果** —— 不用纠结该填什么。

## 坑 D：`build-profile.json5` 里的密码**必须是加密格式**（最费时间的一个）

手动申请的发布证书**没有配套的 `material/` 目录**，而 hvigor 是这么处理密码的：

```js
// hvigor-ohos-plugin/src/utils/decipher-util.js
r.length < 32 && this._logger.printErrorExit("INVALID_DATA", [e]);            // 明文直接退出
r.length % 2 != 0 && this._logger.printErrorExit("INVALID_PASSWORD_LENGTH", [e]);
```

**明文密码过不了这个长度校验**。而解密用的密钥要从 **keystore 同目录下的 `material/`**（`fd` / `ac` / `ce` 三组文件）派生：

```
XOR(material/fd 的三个 16 字节文件 + 固定分量)
  → PBKDF2-SHA256(10⁴ 轮, 盐取 material/ac)
  → AES-128-GCM 解开 material/ce，得到 16 字节密钥
```

`material/` 是 **DevEco 向导或 `devecocli signature generate` 才会生成**的
（官方 FAQ `faqs-signature-service-9`：material 用于加密用户密码，且**与签名材料不是一一对应**）。

**可行做法**（MDwell 上验证过）：复用已有的 `material/` 目录，按上面同样的派生逻辑自己加密密码，
把密文填进 `build-profile.json5`。
注意 `material/` 必须**与 `.p12` 同目录** —— hvigor 是从 `storeFile` 的所在目录去找它的。

> 配置好之后**不要动 `.p12` 的密码**：密文与 `material/` 绑定，换密码要重新加密。

## 坑 E：调试签名与发布签名要能**共存**

换签名 = 清数据（见签名坑 4），所以**不要**把调试签名换掉。正确做法是**另起一套配置**：

```json5
signingConfigs: [
  { name: 'default', ... },   // 调试，原样不动
  { name: 'release', ... },   // 发布材料，指向发布的三件套
],
products: [
  { name: 'default', signingConfig: 'default', ... },
  { name: 'release', signingConfig: 'release', ... },
],
```

对应到模块的 `targets[].applyToProducts` 要把新 product 加进去。

- 打发布包：`devecocli build --product release --build-mode release`
- 日常调试：`devecocli build`（不变）

## 坑 F：release 包**装不上真机**

```
调试签名 + release 模式  →  9568322 signature verification failed due to not trusted app source
发布签名 + release 模式  →  官方 FAQ：「AGC 发布的证书仅支持上架使用，不支持本地安装」
```

调试证书签名的应用**不能以 release 模式安装**；发布证书签名的应用**根本不能本地安装**。

> **推论（很重要）**：凡是**只在 release buildMode 生效**的东西（源码混淆、release 优化），
> **本地都验证不了**。想在真机上跑到混淆后的代码，唯一途径是 AGC 的**邀请测试**。
> **别拿 release 包去 `hdc install` 试** —— 白费功夫。

## 附带：AGC 上的证书名**不能改**

申请时填错名字（比如 `release` 拼成 `realease`）只能删掉重建，而发布证书有配额（一个账号 3 个）。

**但证书名只是 AGC 后台的管理标签** —— 不进证书内容、不影响签名、不影响上架、不会出现在 APP 备案信息里。
**拼错了不值得为它重建。**

# 第三部分：上架打包

```bash
devecocli build clean                                  # 先清
devecocli build --product release --build-mode release # 再全量构建
```

产物：

```
build/outputs/release/MDwell-release-signed.app     ← 上架用这个
```

> `.app` 是上架包，`.hap` 是模块包（装机用）。AGC 上传的是 **`.app`**。

> ⚠️ **先 `clean` 再构建** —— 增量构建可能把调试符号带进 `.app`。
> 注意：这条是**按经验要求执行的步骤**，本机实测**没有复现出体积差异**（三种场景下 `.app` 都是 3 个条目、大小差 ±1 字节）。
> 仍然照做，因为代价只是一个 clean。

## 验证签名身份

```bash
JAR=$DEVECO_SDK_HOME/default/openharmony/toolchains/lib/hap-sign-tool.jar
java -jar "$JAR" verify-app \
  -inFile build/outputs/release/<名>.app \
  -outCertChain /tmp/chain.cer -outProfile /tmp/p.p7b
```

看到 `verify-app success` + `Digest verify result: true` 即通过。
`/tmp/chain.cer` 同样**是证书链**（见坑 B），叶证书在第 2 张。

# 第四部分：源码混淆

**默认是关的**（`entry/build-profile.json5` 的 `buildOptionSet[name=release].arkOptions.obfuscation.ruleOptions.enable`）。
仓库脚手架里 `obfuscation-rules.txt` 已经预置了四个开关（属性 / 顶层 / 文件名 / 导出名），开混淆只需把 `enable` 改成 `true`。

**实测结论（三条，都反直觉）**：

| 事实 | 证据 |
| --- | --- |
| **只在 release buildMode 生效** | 把同样的配置挂到 `buildOption`（通用）或 `buildOptionSet[name=debug]`，debug 构建的 `ets/modules.abc` 与不开混淆时 **md5 完全相同** |
| 混淆确实生效 | release 下 `modules.abc` 从 1,010,944 → 1,001,124 字节 |
| 映射是确定性的 | 两次全量构建的 abc md5 相同，不需要 `-print-namecache` 也能稳定 |

**开了之后本地验证不了**（见坑 F），所以开之前要想清楚。风险点自查：

- **`Record<>` 动态属性访问** —— 官方 FAQ `faqs-arkts-166` 点名的场景：release 下 `T.a` 会取到 `undefined`，
  只有 `T["a"]` 行。混淆前先 `grep -rn "Record<"`。
- **`obj["prop"]` 字符串下标访问** —— 同上。
- **`JSON.parse` 后按属性名取值** —— 同一版本内「自己写、自己读」是自洽的；
  **但跨版本升级时若混淆映射重排，旧数据会读不回来**。
  所以：**要么首次发布就开，要么一直别开** —— 中途开会让老用户的数据读不出来。

# 第五部分：什么时候仍然需要 Windows / macOS

不是所有事 CLI 都能替代：

- **图形化调试器**（断点、变量监视、性能分析器、UI 设计器）—— CLI 给不了，需要 DevEco Studio。
- **AGC 控制台操作** —— 建证书、建 Profile、配地图等按应用身份授权的服务，必须在网页控制台点。
  签名本身 CLI 能做，**但第一次要先去 AGC 把调试设备加上**（见签名坑 0），这一步替代不了。
- **上架提交、隐私政策托管、APP 备案** —— 都是网页流程（见 [08](08-发行与合规.md)）。
- **图形密集的验证** —— 模拟器不如真机。

反过来说，如果诉求是「在 Linux 上写代码、构建、跑 CI、甚至让 AI Agent 独立完成开发闭环」，CLT 这条路是够的。
