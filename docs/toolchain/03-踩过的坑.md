# 03 踩过的坑

**这个文件是本仓库最有价值的部分。** 下面每一条都是在本机（Arch Linux + CLT 26.0.0.851 + `devecocli` 1.3.5
+ Huawei MatePad Mini）上真实踩到、并被核实过的，不是从别处抄来的"常见问题"。

写法约定：**症状 → 为什么容易误判 → 机制/证据 → 怎么做**。

---

## 坑 1：`hdc shell` 无响应（命令挂住，`EXIT=124`）

### 症状

`hdc shell` 或其封装命令不返回，最后超时。`hdc list targets` 却一直显示 `Connected`。

### 为什么容易误判

**这不是设备问题** —— 别据此怀疑设备、参数或 USB 线。链路全程是好的，挂的只是**会话**。

### 机制与证据

命令**确实发到了**设备侧守护进程，只是回复永远不来。而一个会话的工作通道是**串行**的，所以
**一条命令卡住会毒死整个会话** —— 之后每条 `shell` / `file` 都排在它后面，最后统一以 EOF 收场；
控制类命令走另一条路，照旧 10ms 返回。

于是 **`hdc list targets` 全程显示 `Connected`，`dev.sh doctor` 也看不出来**，只有 `hdc shell` 会挂。

证据在 `/tmp/hdc-*.log`（每次 hdc 服务端启动一个文件，滚动保留）：找 `SendToDaemon commandID:1001`
后面没有对应的结果行，最后一条是 `faultInfo:EOF`；同时 `send heartbeat count` 每 5 秒**双向**在跑
而 `messages count` 冻住不动 —— **链路活着、设备侧不回**，这就是"不是设备问题"的直接依据。

实测 2026-10-16 当天 09:51 起的日志里有 **99 条 `faultInfo:EOF`、84 条耗时 ≥20s 的命令**，是常态而非偶发。

### 触发规律（因果未证实）

多次出现在**长时间空闲后的第一条命令**上（实测隔 9 分钟、26 分钟各一次；机器自动熄屏是 600s）。
但**因果未证实**：把熄屏时间覆盖成 60s、空闲 150s 后 `hdc shell` 0 秒就正常返回，**没复现**
—— 所以别当成"休眠就会卡死"来理解。

### 怎么做

恢复三条，按代价从轻到重：

```bash
hdc reconnect <key>                # 只重置会话 + USB 重新枚举，实测约 3 秒恢复，更轻
hdc kill -r                        # 重启服务端，实测 0 秒恢复；影响所有用 hdc 的会话
hdc kill && sleep 2 && hdc start   # 等价于 kill -r，拆开写
```

注意 `reconnect` 只在**健康会话**上实测过（真实卡死状态下还没抓到现场），`kill -r` 才是对真实卡死实测有效的那个；
而且 `reconnect` 的恢复时间**不稳定** —— 实测 4 次里有 1 次超过 15 秒仍然不可用。

### ⚠️ 陷阱：hdc 的退出码会骗人

**判断"设备能不能用"只能靠真实往返。** 实测三个反例：

| 命令 | 输出 | 退出码 |
| --- | --- | --- |
| `hdc reconnect`（不带 key） | `[Fail]Usage: reconnect <target-key>` | **0** |
| `hdc shell`（无可用设备） | `[Fail]ExecuteCommand need connect-key?`（打印到 **stdout**） | **0** |
| `hdc -t <不存在的设备>` | `[Fail][E001005] Device not found or connected` | **0** |

另外两个反直觉点：`hdc list targets` **不是探针**（它由本地服务端回答）；`hdc reconnect` 之后设备
**约 3 秒内 `shell` 仍不可用**（`list targets` 里已经有它，但 `shell` 报 need connect-key）。

**所以探针要用 `hdc shell "echo <标记>"` 并核对输出**，而不是看退码或 `list targets`。

### 预防

- 长会话先 `bash scripts/dev.sh keepawake`（长空闲是已知触发点）。
- **别让两个 Agent / 终端同时压同一台设备** —— 共享一个服务端时，一个卡住的客户端把所有人都堵住。

### 已封装的自动恢复

`scripts/dev.sh` 把上面这套封起来了：短生命周期命令一律带超时，**只有超时（`EXIT=124`）才触发恢复**，
先 `reconnect` 再 `kill -r`，每步用探针校验，然后自动重试一次。手动重置用 `bash scripts/dev.sh recover`；
`doctor` 多了一行真实的 shell 探针。

可调阈值：

| 变量 | 默认 | 含义 |
| --- | --- | --- |
| `HDOS_HDC_TIMEOUT` | 60 | 短命令超时秒数，`0` = 关闭 |
| `HDOS_HDC_INSTALL_TIMEOUT` | 900 | 装包超时 |
| `HDOS_HDC_WAIT` | 15 | 每次恢复后探针轮询的上限 |

把 `HDOS_HDC_WAIT` 设成 `0` 或 `1` 就等于放弃 `reconnect`、直接落到 `kill -r` 这条已验证的路径。
**流式命令（`log` / `errors`）故意不套超时**，否则会把流切断。

## 坑 2：联网的 `devecocli` 子命令被代理静默搞坏

### 症状

`devecocli auth status` 打印 `Not logged in` 且 **`EXIT=0`** —— 看着像"没登录"，实际是代理拦住了。

### 为什么容易误判

因为它**假装成功**：不报错、退出码为 0、信息还特别像真的。

### 怎么做

`auth status` **不能用来判断登录状态**（除非先去掉代理）。凡联网子命令
（`auth` / `signature` / `update` / `emulator image` / `create`）都套一层：

```bash
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY devecocli auth status
```

`docs search` / `docs read` 是本地离线文档，不受影响。
`scripts/dev.sh` 已默认剥掉代理（需要代理时设 `HDOS_KEEP_PROXY=1`）。

## 坑 3：平板锁屏会挡住 `aa start`（`10106102`）

### 症状

```bash
hdc shell aa start -b <包名> -a EntryAbility
# 报 10106102 The device screen is locked
```

### 为什么容易误判

**失败发生在应用启动之前，所以应用侧 API 救不了。** 而且触发条件是**锁屏**、不是熄屏
—— 实测点亮屏幕后 `aa start` 依旧失败，所以"唤醒屏幕"没用。

### 怎么做

覆盖自动熄屏时间。**屏幕不灭就不会锁**：

```bash
bash scripts/dev.sh keepawake             # 默认 24h
bash scripts/dev.sh keepawake 3600000     # 或指定毫秒
bash scripts/dev.sh keepawake-restore     # 收工还原
```

底层就是：

```bash
hdc shell "power-shell timeout -o 86400000"   # 毫秒
hdc shell "power-shell timeout -r"            # 还原
```

实测：设完 `hidumper -s PowerManagerService -a '-s'` 显示 `Timeout=600000ms  OverrideTimeout=86400000ms`，
`-r` 之后 OverrideTimeout 消失、只剩 `Timeout=600000ms`。

### 两个必须知道的代价

1. **会话开始那次解锁仍然只能人工做** —— 自动化绕不过去。所以实机测试前先手动解锁，再跑 `keepawake`。
2. **`-r` 是「恢复默认」，会连带清掉机器上原本就有的 `OverrideTimeout` 设置**（不是还原成原值）。
   收工前先记一下原值：

```bash
hdc shell "hidumper -s PowerManagerService -a '-s'"
```

## 坑 4：签名身份变化会清数据

换签名安装 = **全新安装**，`/data/app/el2/100/base/<包名>` 的 uid 变了，`preferences` 全丢。

- 多台机器开发要**共用同一套 `p12` + `p7b`**。
- 别在 Windows（DevEco 签一套）和 Linux（CLI 签一套）之间交替安装 —— 数据会反复被清。

**相关：别用 `devecocli run --uninstall`** —— 会把 `preferences/` 整个删掉，等于换签名安装的效果，数据全丢。

## 坑 5：`build-profile.json5` 既不能提交也不能忽略

它同时含两样东西：

- 构建必需的 `products` / `modules` 配置 —— **必须**进 Git，否则全新 clone 无法构建；
- 签名后写进去的加密密码 —— **不能**进 Git。

**正确做法**：保持文件被跟踪，用下面这行把本机的签名改动隔离在本地：

```bash
git update-index --skip-worktree build-profile.json5
```

**把它写进 `.gitignore` 是个常见错误。** 同理，签名材料（`*.p12` / `*.cer` / `*.p7b` / `*.csr`）**一律不提交**。

## 坑 6：`compatibleSdkVersion` 与设备/镜像的 API 版本要对齐

- 应用的 `compatibleSdkVersion` **必须 ≤ 目标设备的系统 API 版本**，否则装不上。
- 模拟器同理：**镜像 API 版本必须 ≥ 应用的 `compatibleSdkVersion`**。

本机情况：平板实测 `const.ohos.apiversion` = **26**，与 CLT 自带的 `compatibleSdkVersion 26.0.0` 一致，
所以工程参数不需要调整。

> ⚠️ **`hdc` 的版本号和 SDK/API 版本号是两套体系，不能互相推导。**
> 本机 `hdc` 是 `3.2.0f`（早期还用过 OpenHarmony 的 `3.2.0b`），这跟 `compatibleSdkVersion` 毫无关系。

## 坑 7：hilog 缓冲很小，要抓的日志必须先落盘

设备实测 `hilog -g` 给出 app / core / only_prerelease 各 **512.0K**、init **64.0K**。

**能留多久取决于日志量，不是固定的时长** —— 所以别赌"应该还在"：

```bash
devecocli log --device <serial> --bundle-name <包名> --follow > /tmp/app.log 2>&1 &
```

**必须在应用活着的时候启动**这一条，应用一旦重启，之前的日志就没了。

## 坑 8：热重载的 watch 记得停

`devecocli run --hotreload` 是常驻进程，忘了停会让后续每次构建一直等待。

```bash
devecocli run --hotreload stop      # 或 bash scripts/dev.sh hotreload-stop
```

**别用 `kill` 猜进程名** —— CLI 自己提供了 stop 动作。

## 坑 9：Linux USB 权限 —— 是常见原因，但不是必然

`hdc list targets` 为空时，常见教程会让你加 udev 规则或 `sudo`。但**本机实测不需要**：

> Arch Linux + CLT 自带 hdc，平板接入后 `hdc list targets` 直接就能看到设备，
> **既不需要 udev 规则也不需要 `sudo`**。

所以排查顺序是：**先换线/换口**（USB 直连优于拓展坞/前置面板口），再 `hdc kill -r` 重启服务端，
最后才查 udev 权限。

（顺带记：本机**未安装 `lsusb`**，但也不需要 —— USB 厂商/产品 ID 可从
`/sys/bus/usb/devices/*/idVendor` 读到，本机实测 `12d1` / `1101` / `HDC Device`。）

## 坑 10：UDID 没登记

调试包装不上的头号原因。先跑 `hdc shell bm get -u` 对照 AGC 上的调试设备列表。

注意 **serial 与 UDID 是两个不同的编号，别混用**：

| 项 | 值 |
| --- | --- |
| 型号 | Huawei MatePad Mini（MLR-AL00） |
| serial（`hdc list targets`） | `<平板 serial>` |
| UDID（`hdc shell bm get -u`） | `<平板 UDID>` |

**登记 AGC 调试设备用的是 UDID。**

> 本机的实际取值记在仓库外的 `.env.local`（`HDOS_DEVICE_SERIAL` / `HDOS_DEVICE_UDID`），**不提交** ——
> 设备唯一标识没必要进公开仓库，而这条结论本身不依赖具体取值。

纯 CLI 路径下，它**同时也是签名这一步的前置**（见 [环境搭建](01-环境搭建.md) 的"签名"坑 0）。

## 坑 11：`--no-daemon` 在 CI 里更稳

本地交互式开发可以保留 daemon 换速度；CI / 脚本里建议一律加 `--no-daemon`，
避免 daemon 状态影响结果。
